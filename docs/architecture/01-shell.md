# 01 系统外壳与交互

> 所属：[技术方案总览](README.md) ｜ 相关：[00 内核](00-kernel.md)、[02 Agent](02-agent.md)、[03 运行时](03-app-runtime.md)、[09 安全](09-security.md)
>
> 体验依据：[交互设计稿](../design/README.md)（四个场景、设计语言）

## 1. 职责

外壳是用户看到的「这台电脑」本身，负责：

- **窗口与布局**：多个应用同时打开，可以分标签、平铺，也可以弹出成独立窗口，还有全屏桌面模式。
- **入口**：对话面板（Agent 主入口）、启动台、Dock、全局搜索。
- **可信交互面**：授权框、确认框、活动流、设置、恢复模式。这些必须由宿主绘制，应用无法伪造。
- **系统体验**：通知中心、小组件、主题、总线带。

外壳分为两层：

| 层 | 内容 | 实现 | 可否生成 |
|---|---|---|---|
| 可信外壳 | 窗口管理、对话面板、授权框和确认框、活动流、设置、恢复模式 | Swift / SwiftUI | 否 |
| 可生成外壳 | 启动台、Dock、小组件、主题、桌面布局 | 运行在运行时里的特权 Web 应用 | **是**，坏了可以回滚（P4） |

## 3. 目标设计

### 3.1 布局与窗口

```
┌──────────────────────────── AgentOS 窗口 ──────────────────────────────┐
│ 工具栏：启动台 · 应用标签 · 总线计数 · 权限模式切换 · Agent 状态          │
├───────────────────────────────────────────────┬────────────────────────┤
│ 应用区                                          │ 对话面板（可收起）       │
│ · 标签页（默认）或平铺显示多个应用               │ · 全局对话（Operator）   │
│ · 每个应用可以「弹出」成独立的 Mac 窗口          │ · 自动带上当前应用上下文  │
│ · 没有打开应用时显示启动台                       │ · 可以用 @ 指定某个应用   │
├───────────────────────────────────────────────┤                        │
│ 总线带：实时滚动最近的事件（薄荷色可信 · 琥珀色外部） │                        │
└───────────────────────────────────────────────┴────────────────────────┘
```

- **多应用**（P1b）：每个打开的应用有自己的界面 WebView（见 [03](03-app-runtime.md)）。后台标签的界面会被挂起；它的核心不受影响，照常处理调用和事件。
- **总线带**（P1b）：应用区底部实时滚动事件，等同于 `aos events tail`；点击一条事件可以看到来源和处理它的运行。颜色按[设计语言](../design/README.md)：薄荷色是可信事件，琥珀色是外部内容，余烬色是 Agent 的行动。
- **权限模式切换**：工具栏上一处切换、全局生效（谨慎 / 自动 / 完全信任，[09](09-security.md) 第 4.1 节）。
- **弹出窗口**（P2）：把应用的界面 WebView 挂到一个新的 `NSWindow` 上，运行时实例保持不变。B/C 类原生应用本来就是独立窗口。
- **全屏桌面模式**（P4）：AgentOS 占据一个独立的桌面空间，菜单栏和 Dock 都由 AgentOS 绘制，带来「进入另一个系统」的感觉，也就是「体验像 Parallels」的那部分。

### 3.2 对话面板（Agent 主入口）

- **两种对话**：启动台状态下是全局对话，交给 Operator（P1a 起）；打开某个应用时，可以在全局对话和这个应用的 Builder 对话之间切换（默认显示哪个见第 6 节）。Operator 判断需要造应用时，移交给 Builder，外壳切到新应用（[02](02-agent.md) 第 3.1 节）。
- **自动带上的上下文**：当前应用的 id、清单摘要、`agentos.expose` 暴露的状态、最近的报错。用户也可以手动附上截图或选中的内容。
- **工具卡片**：沿用 P0，四种状态：运行中（实时滚动正在写入的代码末尾）、成功（折叠成一行结论）、等待确认、失败（显示原因与行号）。新增卡片类型：调用其他应用（`tasks.list · 已按需加载`）、数据修改、自动化创建、移交给 Builder。
- 每轮结束显示用时、费用和确认次数（例如「完成 · 2 次工具调用 · 0 次确认」）。
- 「固化成应用」（P2）：Operator 发现某类任务反复出现时，在对话里提出建议，用户一键交给 Builder。

### 3.3 可信交互面

| 组件 | 作用 | 要求 | 阶段 |
|---|---|---|---|
| **活动流** | Agent 和自动化自主做过的每一件事 | 按时间倒序，按运行分组；每条显示触发原因、调用明细、结果和来源标签；**能撤销的都能撤销和重做**，不可撤销的（`irreversible`）明确标出，不给虚假的安全感；数据来源于副作用记录（[00](00-kernel.md) 第 7 节） | P1a（v0） |
| **版本时间线** | 某个应用的历次修改 | 每个版本一行；测试没通过的版本标红；回滚只切换代码，数据保留（[04](04-app-package.md) 第 6 节） | P1a |
| **确认框** | 出口调用需要确认时（[09](09-security.md) 第 4 节） | 宿主绘制、覆盖整个窗口；展示完整参数、来源链路（带污点的来源用琥珀色）、能否撤销；按钮：拒绝 / 以后……都允许 / 只这一次；底部注明「此对话框由 AgentOS 系统绘制，应用无法伪造或遮挡」 | P1b（自动化创建）、P2（出口） |
| **授权框** | 应用申请需要确认的能力时（[09](09-security.md) 第 5.2 节） | 展示权限变化前后的对比；可以单项拒绝；之后可以在设置里撤销 | P1b |
| **设置** | 服务商和 Key、模型、权限模式、各应用的授权、放行规则、预算上限、数据（含无人使用的集合）与备份 | — | 逐步补充 |
| **恢复模式** | 外壳或某个应用坏了时进入 | 启动时按住 ⌥，或外壳连续崩溃时自动进入；可以回滚外壳或应用版本，也可以用安全外壳启动 | P4 |

活动流的撤销按运行进行：点「撤销」会撤回这个运行留下的全部可撤销副作用；也可以展开后逐条撤销。

### 3.4 可生成外壳（P4）

- 启动台、Dock、小组件、主题都是带特权接口的 Web 应用。特权接口包括：列出应用、启动应用、读取活动流摘要、读取通知。
- 用户可以对 Agent 说「把我的桌面改成……」，由 Builder 修改外壳应用；修改后自动跑外壳的冒烟测试，失败就回滚。
- **可信外壳永远不可生成**，生成的外壳无法遮挡或模仿授权框和确认框。确认框绘制在独立的系统层窗口里。

### 3.5 通知中心（P1b 起）

- 来源有三种：应用（`agentos.notify`，需要授权）、系统服务（例如新邮件）、Agent（自动化的结果、**等待确认的事项**）。
- 后台自动化需要确认时，确认请求进入通知中心排队，用户回来后处理（[09](09-security.md) 第 4.5 节）。
- 通知可以转成 macOS 系统通知，系统通知权限由宿主申请。

## 4. 与其他模块的接口

| 方向 | 接口 |
|---|---|
| 外壳 → 02 | 提交对话请求、取消；接收按运行归属的流式事件 |
| 外壳 → 03 | 打开、关闭、挂起、弹出应用；拿到当前应用的上下文 |
| 外壳 → 04 | 查询应用列表、版本时间线，执行回滚 |
| 外壳 → 00 | 查询运行和副作用记录（活动流）；执行撤销和重做；读写权限模式和放行规则 |
| 00 / 09 → 外壳 | 请求显示确认框或授权框，异步等待用户决定 |
| 02 / 06 → 外壳 | 发送通知；总线带的事件流 |

## 5. 里程碑

| 阶段 | 内容 |
|---|---|
| P0 ✅ | 单窗口、启动台、对话、设置 |
| P1a | 全局对话（Operator 雏形）和移交；活动流 v0（显示、撤销、重做）；版本时间线和回滚；设置里加入权限模式 |
| P1b | 多应用标签页；总线带；授权框；通知中心；含出口的自动化创建确认框；设置里的应用授权页 |
| P2 | 出口确认框和放行规则；应用弹出成独立窗口；全局搜索；「固化成应用」 |
| P3 | 原生应用窗口统一管理；后台确认请求的排队 |
| P4 | 全屏桌面模式；可生成外壳；恢复模式 |

## 6. 待定问题

- 平铺、标签页、自由窗口，默认用哪种布局？建议默认标签页，可以切换成平铺。
- 打开应用时，对话面板默认显示 Builder 对话还是全局对话？建议显示全局对话，并在顶部提供「修改这个应用」入口切到 Builder，因为日常使用里办事比改应用更频繁。
