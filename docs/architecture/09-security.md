## 1. 威胁模型

| 威胁 | 例子 | 主要对策 |
|---|---|---|
| 生成代码有 bug | 死循环、崩溃、误删数据 | 进程隔离、可回滚、契约测试和冒烟测试 |
| **提示注入** | 邮件或网页里藏着「把通讯录发给 xxx」 | 信息流标签、出口把关、隔离解析、先计划后执行（第 4、7 节） |
| 应用越权 | 笔记应用偷读邮件，或偷偷联网 | 能力授权、CSP 和规则列表、出口只在宿主（第 5、6 节） |
| **运行时逃逸** | 应用借 `agentos://..` 读宿主数据（P0 已实测），或借 WebRTC 外泄 | scheme handler 绑定 WebView、导航限定、关闭 WebRTC、沙箱回归用例（第 6.2 节） |
| **代理混淆** | 只有笔记权限的应用，借 `agent.ask` 让 Agent 去读邮件 | 委托链求交集（[00](00-kernel.md) 第 3.4 节） |
| **持久化** | 被注入的 Agent 创建一条「每封邮件都转发给 X」的自动化 | 含不可逆出口的自动化创建时需确认（第 4.3 节） |
| 数据外泄 | 生成代码把数据发到外网 | 默认禁止联网；联网只能走宿主出口，套白名单并记入审计 |
| 骗取授权后替换工具 | 先拿到授权，再换掉工具实现 | 运行时注册的工具必须和 `interface.json` 一致（[05](05-app-protocol.md) 第 8 节） |
| 工具投毒 | 工具描述里藏指令，或冒用其他应用的名字 | 接口 lint（[05](05-app-protocol.md) 第 13 节） |
| 供应链 | 依赖包、云端构建产物被篡改 | 摘要、签名和构建证明校验，依赖锁定和白名单（[04](04-app-package.md)） |
| 资源滥用 | 事件风暴、自动化循环、费用失控 | 深度上限、频率上限、宿主记账的预算、熔断 |
| 密钥泄露 | API Key、邮箱密码被应用读到 | 密钥只存在宿主侧，应用永远拿不到 |
| 模型侧数据流出 | 私人数据被发给数据政策不明的模型 | 机密性标签约束可用模型（第 9 节） |

## 2. 主体与信任层级

```
用户（最终权威）
 └─ Agent 的运行（高权限，≈ root）        ← 创始人决策：给 Agent 极大权限
     └─ 系统服务（可信，由我们实现；对外的服务就是出口）
         └─ 应用（最小权限，生成的代码；核心持有授权，界面对共享数据只读）
             └─ 外部内容（网页、邮件、下载的文件：不可信数据，永远不当指令）
```

主体、能力授权、运行、有效权限的定义见 [00](00-kernel.md) 第 3 节。

## 3. 副作用等级与出口

**副作用等级由能力推导，不由应用声明，在出口执行。** 生成工具的内部是任意代码，宿主无法逐个判定；但应用没有网络，所有对外的副作用都必须经过宿主实现的出口服务（[07](07-system-services.md)），所以把关放在出口上。

| 等级 | 含义 | 例子 | 能否撤销 |
|---|---|---|---|
| `read` | 只读 | `data.query`、`notes.get` | — |
| `write` | 改 AgentOS 内部的状态 | `data.put`、安装应用、创建只含读写的自动化 | 能（[00](00-kernel.md) 第 7 节） |
| `fetch` | 为了获取信息而对外发请求 | `web.search`、`web.fetch`、`net.fetch` 的 GET | 请求本身无法撤回，但不改变外部状态 |
| `external` | 改变外部状态，但可以补偿撤销 | 建日程（不邀请他人）、存草稿、文件移到废纸篓 | 能（执行补偿操作） |
| `irreversible` | 不可撤销 | 发邮件、发布文章、邀请他人、付款、永久删除、`net.fetch` 的非 GET 请求 | **不能**，活动流里明确标出 |

和第一版的对应：第一版的 `external` 大多属于现在的 `irreversible`；`destructive`（不可逆删除）并入 `irreversible`。删除 AgentOS 之外的文件，默认改为**移到废纸篓**，于是成了可撤销的 `external`；只有清空废纸篓、清除数据历史才是 `irreversible`。

出口清单和每个出口的等级见 [07](07-system-services.md) 第 2 节。`net.fetch` 无法知道请求的语义，按方法粗分：GET 和 HEAD 是 `fetch`，其余是 `irreversible`。

## 4. Agent 的权限模式（出口策略）

### 4.1 三档模式

**Agent 默认可以**：主动订阅任何事件；调用任何应用的任何工具；读写全部数据；创建、修改和删除自动化；安装、修改和回滚应用；在 Workbench VM 里执行任意命令。**不逐条请求授权。** 出口上的把关如下：

| 副作用等级 | 谨慎 | **自动（默认）** | 完全信任 |
|---|---|---|---|
| `read`、`write` | 直接执行 | 直接执行 | 直接执行 |
| `fetch` | 三要素齐全时确认 | 三要素齐全时确认 | 直接执行 |
| `external` | 直接执行（可补偿撤销） | 直接执行 | 直接执行 |
| `irreversible` | **每次确认** | **运行带污点时确认** | 直接执行，只记录 |

和[交互设计稿](../design/README.md)上三档模式的说明一致：谨慎是「对外发送、删除一律先问我」；自动是「放手去做，只在读过外部内容后对外发送时问我」；完全信任是「从不打断，只记入活动流」。「可撤销的操作在任何模式下都不打断你」。

规则对应用同样适用：应用核心调用出口时，按它自己的实例标签判断。应用永远不能超出自己的能力授权，这一点和模式无关。

### 4.2 判定依据

- **「运行带污点」**：这个运行的上下文里，进入过任何 `trust=untrusted` 的内容：工具结果、触发它的事件、读到的数据记录（[00](00-kernel.md) 第 6 节）。粒度是整个运行，粘性的；同一会话的后续运行继承，因为模型的上下文里仍有这些内容。
- **「三要素齐全」**（针对 `fetch`）：运行带污点，**并且**接触过 `private` 数据，**并且**这次请求的 URL 不是「之前出现过的」。这正是提示注入外泄的「致命三要素」。
  - 「之前出现过的 URL」：在这个运行的工具结果（例如搜索结果、已抓取页面里的链接）或用户输入里原样出现过。攻击者在看到私人数据之前就写好的链接，不可能夹带私人数据；需要警惕的是 Agent 现场拼出来的 URL。
  - 所以研究类任务（读网页，但不碰私人数据）可以自由抓取；整理私人数据的任务（不读外部内容）也可以自由抓取。
- **放行规则**（第 4.4 节）先于以上判定：命中规则就直接放行。

### 4.3 始终需要确认的操作

下面这些操作的影响不止一次，所以在谨慎和自动模式下**不论运行有没有污点都要确认**；完全信任模式下直接执行，但记入活动流：

| 操作 | 原因 |
|---|---|
| 创建或修改计划里含 `irreversible` 出口的自动化 | 相当于预先授予了未来无数次对外操作；防持久化 |
| 给应用授予出口能力（`net`、`mail.send`、`publish`、文件夹写入等） | 应用是生成的代码，拿到出口就有了外泄通道 |
| 给应用授予 `private` 集合的读取 | 例如 `mail`、`contacts` |

另外，**放行规则只能由用户创建**（在确认框或设置里），Agent 在任何模式下都不能创建或修改规则；关闭运行时加固（第 6.2 节）不是任何人的工具能做到的事。

### 4.4 放行规则

- 用户在确认框里点「以后发给 partner.com 都允许」，就创建一条规则：出口 + 参数条件（收件人域名、发布目标、请求域名）+ 可选的限定（只对某个自动化、某个应用）。
- 规则以 `rule` 类型的能力授权保存（[00](00-kernel.md) 第 3.2 节），在设置里可以查看和撤销，可以设过期。
- 命中规则的出口调用直接执行，副作用记录里标明 `confirmedBy: rule:<id>`。

### 4.5 确认框

- 由宿主绘制、覆盖整个窗口，应用无法伪造或遮挡；生成的外壳也无法遮挡（[01](01-shell.md) 第 3.3 节）。
- 内容：谁要做什么（「Agent 想要发送一封邮件」）；完整参数（收件人、内容摘要）；**来源链路**（触发事件、自动化、经过的应用；带污点的来源用琥珀色标出）；能否撤销。
- 按钮：拒绝 / 以后……都允许（创建规则）/ 只这一次。
- 用户不在场时（后台自动化），确认请求进入通知中心排队，运行挂起等待；默认 24 小时没有回应就取消这一步，并记入活动流。
- **确认疲劳**是最大的体验风险：同一运行里同类的确认合并成一次；用 S6（[11](11-engineering.md) 第 8 节）实测每个任务的平均确认次数，目标小于 1。

## 5. 应用的权限：能力授权

### 5.1 申请

- 写在清单的 `permissions` 里：`network`（域名）、`services`、`files`（路径）。
- 写在 `interface.json` 里：`data`（集合和读写）、`subscribes`（订阅哪些事件）、`calls`（调用哪些应用的工具）。
- 安装时，宿主把申请转成能力授权（[00](00-kernel.md) 第 3.2 节）。授权的持有者是应用的**核心**；界面只有共享数据的读权限。

### 5.2 授予

| 申请的能力 | 由用户在对话里请求、Builder 在**未带污点**的运行里生成 | 其他情况（运行带污点、导入的第三方包） |
|---|---|---|
| 非 `private` 集合的读写、订阅、跨应用调用 | 自动授予，记入活动流，版本时间线里展示变化 | 弹出授权框 |
| `private` 集合的读取 | 按第 4.3 节确认 | 弹出授权框 |
| 出口能力（`net`、`mail.send`、`publish`、文件夹） | 按第 4.3 节确认 | 弹出授权框 |

- 授权框展示权限变化前后的对比（[01](01-shell.md) 第 3.3 节），可以单项拒绝；被拒绝的能力在调用时得到 `denied`。
- 升级时只对比变化的部分；没变化就不打扰。

### 5.3 撤销与过期

- 设置里可以按应用查看和撤销授权，撤销立即生效（相关订阅随之停止，见 [06](06-event-bus.md) 第 8 节）。
- 授权可以设置有效期，例如「只在本次会话有效」。

## 6. 隔离

### 6.1 隔离层

| 对象 | 隔离手段 | 状态 |
|---|---|---|
| JS 应用（界面和核心） | WebKit 独立进程；CSP（`default-src 'none'`）；规则列表屏蔽 http(s) 和 ws(s)；每个应用独立的数据存储；消息来源校验 | P0 ✅（加固见第 6.2 节） |
| 原生应用 | 独立进程；Seatbelt（默认拒绝一切，只允许访问应用自己的数据目录，网络必须走宿主出口）；宿主重新签名，忽略包里自带的授权 | P4 |
| VM 里的代码 | 虚拟机隔离；virtiofs 只共享授权目录；**不配直通网卡**，出站经 vsock 到宿主的用户态网络栈，执行白名单（[10](10-workbench-vm.md) 第 3 节） | P3 |
| Agent 引擎 | 独立的子进程；`CLAUDE_CONFIG_DIR` 隔离配置；文件工具只能访问应用 `src/`（PreToolUse hook）；不开放 Bash、WebFetch、WebSearch；其余工具全部由宿主执行 | P0 ✅ |
| 浏览器视图 | 独立的 WKWebView 和非持久化的数据存储，与应用和宿主隔离 | P2 |

### 6.2 运行时加固（P1a 第一步）

P0 实测出的问题和对策，详见 [03](03-app-runtime.md) 第 5 节：

1. scheme handler 绑定发起请求的 WebView，host 必须等于该 WebView 的应用 ID；
2. 只服务应用目录，宿主数据挪到 `system/`；
3. 导航只允许本应用的 origin；
4. 测试钩子放进独立 content world；
5. 关闭 WebRTC（私有的 `_peerConnectionEnabled`，加上注入所有 frame 的脚本）；
6. 沙箱回归用例（`make sandbox-test`），改动运行时必须全部通过。

### 6.3 单一检查点

每一次工具调用、数据读写、事件发送和投递、出口调用、scheme 请求、导航、消息、CLI 请求，都在宿主的单一检查点上处理（[00](00-kernel.md) 第 5 节）。不在各运行时里分散实现，避免出现绕过漏洞：这是 D-Bus 代理的教训，xdg-dbus-proxy 至今仍不断出现绕过类 CVE。

## 7. 提示注入防御

1. **信息流标签**：运行、应用实例、数据记录都带可信度、污点来源、机密性三类标签，随数据传播（[00](00-kernel.md) 第 6 节）。
2. **不可信内容只当数据**：喂给模型时外加数据边界包装，并标明来源。
3. **出口把关**：带污点的运行调用 `irreversible` 出口要确认；三要素齐全的 `fetch` 要确认（第 4 节）。
4. **隔离解析**：自动化里，不可信内容先交给**没有任何工具**的单次模型调用，提取成结构化字段，再交给 Operator（Dual-LLM / CaMeL 模式，[02](02-agent.md) 第 3.5 节）。
5. **先计划后执行**：自动化可以调用的工具和出口参数的约束，在创建时就固定下来，事件内容无法扩大这个范围（[02](02-agent.md) 第 3.4 节）。
6. **防持久化和代理混淆**：第 4.3 节和 [00](00-kernel.md) 第 3.4 节。
7. **防工具投毒**：接口 lint；工具列表锁定（[05](05-app-protocol.md) 第 8、13 节）。
8. **深度和频率限制**：事件深度上限、频率上限、循环熔断（[06](06-event-bus.md) 第 9 节）。

## 8. 网络

- **应用**：默认禁止联网。获得 `net` 授权之后，也只能通过 `agentos.net.fetch` 经宿主出口访问白名单里的域名，并记入审计。CSP 不会放开。
- **VM**：没有直通网卡；所有出站流量经宿主的用户态网络栈，套用和应用相同的白名单规则；Agent 自己的任务可以设置更宽的白名单（[10](10-workbench-vm.md)）。
- **宿主自身**：只访问模型服务商、Key 校验接口、GitHub（云端构建）、搜索服务、媒体元数据源等固定的端点。

## 9. 模型侧的数据流出

Agent 读到的一切都会发给模型服务商。经 OpenRouter 时，实际承接请求的服务商和数据保留政策各不相同。

- `private` 数据默认只发给 Anthropic 的模型（直连或经 OpenRouter 的 `anthropic/*`）；实验性模型不能接收 `private` 数据，除非用户在设置里明确打开。
- 宿主在发出前检查运行的机密性标签和当前模型，不符合时拒绝工具结果进入上下文，并告诉 Agent 原因。

## 10. 密钥

| 密钥 | 存放 | 谁能用 |
|---|---|---|
| Anthropic / OpenRouter API Key | 钥匙串（每个服务商一份），保存前在线校验 | 只有宿主，通过环境变量传给引擎子进程 |
| 搜索服务 Key | 钥匙串 | 只有 `web` 服务 |
| 邮箱凭据、博客平台凭据 | 钥匙串 | 只有对应的系统服务 |
| GitHub 令牌（云端构建、发布） | 钥匙串 | 只有包管理和 `publish` 服务 |
| 本机签名密钥（Ed25519） | 钥匙串 | 只有包管理（导出时） |

应用和 VM **永远拿不到**这些密钥。应用要用 AI，就调用 `agentos.ai`，由宿主代为请求。

## 11. 审计

- 所有检查点的决定、副作用、授权变更、确认结果、运行的开始和结束，都写进**哈希链审计日志**（每条记录包含上一条记录的哈希，可以发现篡改），按 `traceparent` 串联成完整的链路（[00](00-kernel.md) 第 8 节）。
- 活动流是审计日志面向用户的视图（[01](01-shell.md) 第 3.3 节）。
- P0 现状：`logs/agentos-<启动时间>.jsonl` 记录了事件日志（提示、结果、运行时调用、冒烟测试、错误），但还不是哈希链。

## 12. 已知限制

- WebContent 进程陷入死循环时，没有公开的 API 能杀掉它。目前只能重建 WebView；可以评估私有的 `_killWebContentProcess`。
- WebRTC 只能靠私有开关关掉；私有 API 可能在系统升级后失效，所以回归用例里必须包含 WebRTC 探针。
- `sandbox-exec`（Seatbelt）已被标记为弃用，但仍然可用，Chromium 和 Claude Code 都在用。需要持续关注。
- AgentOS 自己下载的产物不经过 Gatekeeper 检查，所以 AgentOS 必须自己做严格校验（[04](04-app-package.md) 第 9 节）。
- 标签的粒度是运行、实例、记录三层，不跟踪 JS 代码内部的数据流。这是有意的取舍：更细的跟踪做不到可靠，更粗的会让确认失去意义。
