# Web/JS 与 Native 编译两套运行时方案对比

> 2026-10-15 ｜ 实测环境：MacBook M5 Pro，macOS 26.5.1，Xcode 26.6 / Swift 6.3.3
>
> 实验代码见 [native-experiments/](native-experiments/)。Web 方案的数据来自 [webkit-experiments/](webkit-experiments/) 和 P0 原型的自测。

## 0. 结论

- **「直接生成机器码」实际上是「生成源码，在本机编译」。** 大模型无法可靠地直接输出机器码或汇编，即使能，也比不上编译器，而且是一段无法审查的二进制。所以 Native 方案的真实形态是：Agent 生成 Swift / Metal 源码 → 本机 `swiftc` 编译 → 加载运行。
- **编译速度不是瓶颈。** 单文件游戏编译只要 0.3–0.7 秒，新二进制首次加载约 0.5 秒。比起模型生成代码的几十秒，可以忽略。
- **真正的问题在隔离、稳定性和分发。**
  - **进程内加载**（dlopen）：生成代码一崩溃宿主就跟着退出；加载过的版本无法卸载；生成代码拥有宿主的全部权限，包括读取钥匙串里的 API Key。
  - **进程外运行**能解决隔离问题，但 macOS 没有公开 API 把另一个进程的界面嵌进左侧面板。
  - **两种方式都要求用户装 Xcode 或 Command Line Tools。**
- **建议：分层，不替换。**
  - Web/JS 继续做默认运行时。
  - 用 Swift 实现 `agentos.*` 能力桥，把原生能力按权限开放给 Web 应用。
  - 另设一个可选的「原生模式」：独立进程 + Seatbelt 沙箱，处理 Web 做不到的场景。
  - 不做进程内 dylib 加载。

## 1. 三种具体形态

| 形态 | 做法 | 本质 |
|---|---|---|
| **W：Web/JS（当前）** | Agent 生成 HTML/JS；每个应用一个 WKWebView，从 `agentos://` 加载 | 解释执行 + JIT，跑在 WebKit 的独立进程里 |
| **N1：Native 进程内** | Agent 生成 Swift；编译为 `.dylib`；宿主 `dlopen` 后取出 `NSView` 放进左侧 | 机器码，跑在宿主进程里 |
| **N2：Native 进程外** | Agent 生成 Swift；编译为可执行文件；在 Seatbelt 沙箱里作为子进程运行 | 机器码，跑在独立的受限进程里 |

## 2. 实测数据

### 编译（swiftc 6.3.3，单文件贪吃蛇，约 100 行）

| 场景 | 耗时 |
|---|---|
| AppKit，`-Onone`，冷模块缓存 | 3.34 s |
| AppKit，`-Onone`，热缓存 | **0.32 s** |
| AppKit，`-O`，热缓存 | 2.85 s |
| SwiftUI（`@Observable` + `Canvas` + `TimelineView`），`-Onone` | **0.46 s** |
| SwiftUI，`-O` | 0.68 s |
| SwiftUI，Swift 6 严格并发模式，首次 | 2.69 s |
| 编译为独立可执行文件 | 0.34 s |

编译时还遇到一个插曲：手写的 SwiftUI 版本第一次就编译失败了。原因是 `@Observable` 宏不支持一行声明多个变量（`var cols = 26, rows = 20`）。这类语言细节的坑，模型同样会踩。

### 加载与运行

| 场景 | 结果 |
|---|---|
| 新编译 dylib 首次 `dlopen` 并创建视图 | **450–680 ms**，原因是 macOS 对没见过的二进制做安全扫描 |
| 同一个 dylib 再次加载 | 约 1 ms |
| 同一模块名重新编译后再加载 | ObjC 运行时警告 `Class … is implemented in both …`，「使用哪一个是未定义的」，所以每个版本都必须换模块名 |
| `dlclose` | 返回 0，但镜像仍然留在内存里，**无法卸载**，每迭代一次内存就增长一次 |
| 生成代码数组越界 | `Fatal error: Index out of range`，**宿主进程直接退出** |
| 独立进程从启动到窗口出现 | 首次约 630 ms，之后 120–140 ms |
| Seatbelt（`sandbox-exec`）限制子进程 | 禁网有效（curl 失败），禁读 `~/Documents` 有效，AppKit 游戏照常运行 |

### Web 方案对照（来自之前的实测）

| 项 | 结果 |
|---|---|
| 修改代码后重新加载 | 4–6 ms |
| 新建一个 WebView（热） | 46 ms |
| 帧率 | 约 60 fps 上限（120Hz 屏幕上也一样） |
| 崩溃或死循环 | 发生在 WebContent 进程里，宿主不受影响；死循环会让该进程持续占用 CPU |
| 外网访问 | CSP 加内容规则列表，四条通道全部拦截 |

## 3. 优缺点与能力边界

| 维度 | W：Web/JS | N1：Native 进程内 | N2：Native 进程外 |
|---|---|---|---|
| **迭代延迟** | ✅ 约 5 ms | 🟡 约 1 s（编译加首次加载） | 🟡 约 1 s（编译加启动） |
| **2D 游戏** | ✅ Canvas 足够 | ✅ | ✅ |
| **3D / GPU** | ✅ WebGL2、WebGPU | ✅✅ Metal 全特性 | ✅✅ Metal 全特性 |
| **帧率** | 🟡 上限约 60 fps | ✅ 支持 120Hz ProMotion | ✅ 支持 120Hz ProMotion |
| **CPU 密集计算** | 🟡 JS JIT；可用 Wasm 接近原生 | ✅✅ SIMD、多线程、Accelerate | ✅✅ |
| **原生观感**（控件、菜单、拖放、无障碍） | 🟡 只能用 CSS 模仿 | ✅✅ 真正的 AppKit / SwiftUI | ✅✅ |
| **系统能力**（任意文件、相机、蓝牙、USB、AppleScript、辅助功能、CoreML、Vision、端侧模型） | ❌ 只能通过宿主逐个桥接 | ✅ 全部可用 | ✅ 全部可用，受沙箱规则约束 |
| **网络隔离** | ✅✅ 默认全禁，可按域名放开 | ❌ 无法限制 | ✅ 由 Seatbelt 控制 |
| **权限隔离** | ✅✅ 独立进程，拿不到 Key | ❌ 拥有宿主全部权限，**可读钥匙串里的 API Key** | ✅ 代码签名不同，读不到宿主的钥匙串项 |
| **崩溃和卡死** | ✅ 不影响宿主 | ❌ 宿主一起崩溃 | ✅ 不影响宿主 |
| **热更新** | ✅ 可以保留状态 | ❌ 不能卸载，每个版本都要新模块名，内存只增不减 | ✅ 重启子进程即可，干净 |
| **嵌入左侧面板** | ✅ 直接嵌入 | ✅ 直接嵌入 NSView | ❌ **没有公开 API**，见第 4 节 |
| **依赖** | ✅ 系统自带 WebKit | ❌ 需要 Xcode 或 CLT（GB 级），macOS SDK 按许可不能随 App 分发 | ❌ 同 N1 |
| **分享与移植** | ✅ 一个 HTML 文件到处都能跑 | ❌ 只能在 macOS 上跑，分发要签名和公证 | ❌ 同 N1 |
| **模型生成可靠度** | ✅✅ 训练数据最多，Canvas 游戏非常成熟 | 🟡 SwiftUI 每年都有 API 变化，Swift 6 并发和宏错误多；好在编译器报错精确，修复闭环快 | 🟡 同 N1 |
| **自测工具** | ✅ P0 已实现（帧计数、截图、状态读取、模拟输入） | 🟡 需要重做：视图截图、注入 NSEvent | 🟡 需要跨进程重做 |

## 4. N2 的嵌入问题

macOS 没有公开 API 把另一个进程的视图嵌进自己的窗口。可选做法如下：

1. **单独开窗口**：最简单，失去「左侧即时出现」的体验，但适合「原生模式」这种进阶场景。
2. **IOSurface 远程渲染**：
   - 子进程把画面渲染到 IOSurface，通过 XPC 或 mach port 共享给宿主，宿主作为 `CALayer` 的内容显示。
   - 键盘和鼠标由宿主经 IPC 转发给子进程。
   - 适合游戏和 Canvas 类应用，代价是多约 1 帧延迟；文本输入、输入法、无障碍支持会很麻烦。
3. **私有 API（`CALayerHost` / `CAContext`）**：Chromium 在 macOS 上就是这么做的。我们不上架，所以可以用，但随系统升级可能失效。
4. **ExtensionKit 远程视图**：要求扩展在构建时打进已签名的 App，不适合运行时动态生成。

## 5. 建议的分层路线

| 层级 | 内容 | 用在什么场景 | 优先级 |
|---|---|---|---|
| **L0：Web/JS**（已有） | 默认运行时 | 游戏、工具、可视化，覆盖绝大多数请求 | 已完成 |
| **L1：能力桥 `agentos.*`** | 用 Swift 实现，按应用授权，再暴露给 Web 应用：文件（用户选择）、通知、剪贴板、相机和麦克风、系统信息、`agentos.ai`、端侧模型 | 「需要原生能力」的大部分需求，不需要生成原生代码 | **P1–P2** |
| **L1.5：WebAssembly** | Agent 生成 C/Zig/Rust 代码编译成 Wasm，在 WebView 里运行 | 物理模拟、图像处理等计算密集部分 | P2，按需 |
| **L2：原生模式**（可选） | Agent 生成 Swift 包，本机编译，在 Seatbelt 沙箱子进程里运行；先单独开窗口，再考虑 IOSurface 嵌入；也可以导出成真正的 `.app` | Metal 重度渲染、120Hz、深度系统集成、想要一个独立 `.app` | P3 |
| ~~N1：进程内 dylib~~ | — | 不做：崩溃、权限、无法卸载三个问题都无法解决 | — |

L2 落地前要做的事：

- 运行时检查 `xcode-select -p`，没有工具链时引导用户安装 CLT。
- Seatbelt 用 `deny default` 加白名单的规则：只允许读写应用自己的目录，禁止联网和访问钥匙串。`sandbox-exec` 已被标记为弃用但仍然可用，Chromium 和 Claude Code 等都在用。
- 每个版本使用独立的产物目录。
- 编译错误作为工具结果回传给 Agent。
- 为原生应用另写一份系统提示和 Skill：固定 Swift 5 语言模式，限定可用的 API 范围。
