## 0. 结论速览

**总体判断：方向可信，地基扎实，但上层设计「宽而浅」。** 运行时和底座的选择有实测支撑，P0 已经跑通；协议、总线、数据层、权限这几块（也就是差异化所在）目前全部停留在纸面，而且彼此之间有几处没对齐的地方。P1 一口气覆盖 8 个模块，范围过大。

| 模块 | 证据等级 | 可信度 | 主要问题 |
|---|---|---|---|
| 03 Web 运行时 | 实测 + 已实现 | 高 | 本次实测发现越界读取漏洞（第 2 节），修复成本低 |
| 10 工作间 VM | 实测（启动、快照、内存） | 中高 | 「NAT + 出站代理」自相矛盾；要求 macOS 26，和工程的 macOS 15 最低版本冲突；Containerization 仍未到 1.0 |
| 03/04 原生 B 类 | 实测（编译、Seatbelt） | 中高 | 不在关键路径上，可以后置 |
| 02 Agent 引擎（Builder） | 已实现 | 高 | 扩到 Operator 和自动化后，进程模型和成本模型没设计 |
| 04 C 类云构建 | 调研 | 中 | 政策红线调研充分；对个人 OS 的价值存疑，建议无限期后置 |
| 05 应用协议 | 调研 + 纸面 | 中 | 生成应用怎样「无界面执行」没验证；把 MCP 当真相源风险高；命名和归属有歧义 |
| 06 事件总线 | 纸面 | 中 | 设计本身标准，但 P1 范围过大；与数据层的变更事件大量重叠 |
| 08 数据层 | 纸面 | 中 | 方向对；集合归属、工具与数据接口的分工没定 |
| 09 权限与安全 | 纸面 | **中低** | 「自动模式」依赖的污点机制排在 P3，但不可信内容在 P2 就进来了；effects 判定不可操作；存在代理混淆和持久化攻击面 |
| 01 外壳 | 部分实现 | 高 | 确认框疲劳是最大的体验风险 |
| 11 工程 | 已建立 | 中 | 没有 Swift 测试目标和 CI；分发链路（公证）没验证 |

**三个最重要的判断：**

1. **安全模型需要在动工之前重新收口。** 现在的方案里，Agent 拥有 root 级权限，默认的「自动」模式靠「上下文里有没有不可信内容」决定要不要确认；但污点机制排在 P3，而网页和发布服务在 P2 就上线了。把关点也放错了位置：不该靠宿主逐个判定生成工具的副作用，而应该在少数几个可信的**出口（sink）**上执行。见第 3.1–3.3 节。
2. **「每个应用都是 MCP Server」能否成立，取决于一个没被验证的前提：生成的 JS 应用能在不打开界面的情况下可靠地执行工具和处理事件。** 建议把应用拆成「无界面核心 + 界面」两部分，这同时解决无界面执行、接口和界面能力一致、契约测试这三个问题。见第 3.4–3.5 节。
3. **P1 应该切成两半。** 先做内核对象模型、应用模型、数据层和单应用协议，再做应用互联和订阅。见第 5 节。

**先行的核心设计（按顺序）：**

| # | 设计 | 一句话 |
|---|---|---|
| D1 | 内核对象模型与单一检查点 | 主体、能力、运行（Run）、效果日志四个对象，所有入口经同一个检查点 |
| D2 | 应用模型与接口定义（IDL） | 无界面核心加界面；IDL 是真相源，MCP、CLI、TS 存根都是投影 |
| D3 | 数据层 v1 | 集合、共享 schema、历史与撤销、变更事件 |
| D4 | 权限策略与出口把关 | 在出口上把关；运行级和实例级污点；三档模式的精确定义 |
| D5 | Agent 引擎架构 | Builder 和 Operator 的会话模型、元工具、Run 集成、轻量模型调用 |
| D6 | 总线 v1（收窄） | 先只做数据变更和系统事件，以及持久订阅 |
| D7 | 包与版本 v1 | git 加版本快照加回滚，签名后置 |

## 2. 实测发现：P0 沙箱可以越界读取宿主数据

### 2.1 现象 [实测]

生成的应用可以把自己导航到 `agentos://..`，以 `agentos://..` 这个 origin 同源读取 `~/Library/Application Support/AgentOS/` 下的任意文件，再把结果放进 URL 片段，导航回自己的 origin。探针 3 读到了 `meta/<id>/manifest.json`、`logs/selftest-result.json`，均为 200。

原因 [代码]：

- `AppSchemeHandler` 直接用 URL 的 host 拼目录：`Paths.appDir(appId)`，`appId` 没有校验。host 为 `..` 时，基准目录就变成了数据根目录，后面的前缀检查也就形同虚设（`App/Runtime/AppSchemeHandler.swift`）。
- 一个 scheme handler 服务所有 WebView，不核对「发起请求的 WebView 属于哪个应用」。
- 导航策略放行所有 `agentos:` URL，不限定本应用的 host（`RuntimeController.decidePolicyFor`）。

**今天的影响有限：** 应用不能联网，读到的东西带不出去；日志文件名是秒级时间戳，需要猜。**到 P1 就是严重漏洞：** 按 [08](../architecture/08-data.md) 和 [06](../architecture/06-event-bus.md) 的设计，`data/store.sqlite` 和 `bus.sqlite` 都放在这个根目录下，文件名固定。任何生成的应用都能绕过能力授权，读到全部个人数据和事件日志，再通过它拿到的 `network` 授权带出去。

### 2.2 修复（几行代码）

1. host 必须是注册表里存在的应用 ID（UUID 格式），并且必须等于发起请求的 WebView 所属的应用。
2. 导航只允许本应用的 host，以及 `about:blank`。
3. scheme handler 只映射 `apps/<id>/`，宿主数据目录（`meta/`、`logs/`、`agent/`，以及将来的 `data/`、`bus.sqlite`）挪出这棵树，或者放到单独的根目录下。
4. 把三个探针加进 `tests/fixtures/`，成为沙箱回归用例。

### 2.3 同时发现的小问题

| 问题 | 来源 | 影响 | 建议 |
|---|---|---|---|
| `RTCPeerConnection` 可用，ICE 收集会正常进行 | [实测] | CSP 的 `connect-src` 和内容规则列表都管不到 WebRTC。用户名、凭据会被发给 TURN 服务器，这是公认的外泄通道（2 秒内没拿到 srflx 候选，所以本次没确认 STUN 包真的出了网） | P1 前关掉 WebRTC。WKWebView 没有公开开关，只有私有的 `_peerConnectionEnabled`（第 6 节）；只在 shim 里删掉构造函数不够，同源 iframe 拿得到原始的全局对象（见下一条） |
| 同源 srcdoc iframe 没有 shim | [实测] | shim 只注入主 frame（`forMainFrameOnly: true`），iframe 里的全局对象是干净的 | 任何「在 shim 里禁用某个 API」的做法都要考虑 iframe |
| `window.__agentos` 是普通的可写全局变量；宿主在 page world 里执行 `evaluate` | [实测] [代码] | 应用可以伪造帧数和状态，让冒烟测试通过。P0 无所谓，但 P1 的契约测试和工具调用不能建立在这上面 | 宿主钩子放进独立的 `WKContentWorld`，[03](../architecture/03-app-runtime.md) 已有规划，要在 P1 一开始就做 |
| `PreToolUse` hook 只检查 `file_path` 和 `path` | [代码] | `Glob` 的 `pattern` 如果写成绝对路径，可能列出应用目录以外的文件名（`Read` 仍会被拦） | 同时检查 `pattern` |

**教训：**「单一检查点」不能只管 MCP 调用。scheme handler、导航、消息桥是运行时的三个入口，它们同样属于检查点的范围。这一点应写进 D1。

## 3. 关键问题（按严重度）

### 3.1 路线图顺序：不可信内容比污点机制先上线 【高】

- 默认的「自动」模式规定：external 和 destructive 操作直接执行，**只有当 Agent 的上下文里混入不可信内容时才确认**（[09](../architecture/09-security.md) 第 3 节）。
- 但「污点传播全面落地」排在 P3（09 第 11 节），而 `web.search`、`web.fetch`、浏览器和 `publish` 都在 P2（[07](../architecture/07-system-services.md) 第 5 节）。
- 结果：P2 的研究助手读到一个带注入的网页，就有可能在不弹确认的情况下调用 `publish`。

**建议：** 把「运行级污点」（第 3.2 节）加上出口把关，作为 P2 的发布门槛；或者规定在污点机制完成之前，默认模式是「谨慎」。

### 3.2 「Agent ≈ root + 自动模式」需要一个可执行的污点定义 【高】

LLM 上下文里的污点是**粘性的、二值的**：Operator 只要读过一个网页，这次会话就一直带着污点。研究助手、邮件处理这类主线任务一开始就要读外部内容，所以自动模式实际上会退化成谨慎模式；反过来，如果污点跟踪不准，它就形同虚设。

生成的 JS 代码内部怎么「派生」数据，宿主看不见，所以 [08](../architecture/08-data.md) 第 7 节说的「派生数据继承污点」没有执行机制。可执行的做法只有粗粒度的标签：

| 标签作用在 | 规则 |
|---|---|
| **运行（Run）** | 一次 Agent 运行只要有 `trust=untrusted` 的工具结果进入上下文，整次运行就带上污点 |
| **应用实例** | 一个应用实例（WebView）只要收到过带污点的数据，此后它写入的一切都带污点，直到重载 |
| **记录** | 数据层记录带 `_taint`；读到它的运行或实例随之带上污点 |

再配合三条措施降低确认的频率：自动化先计划后执行（创建时固定收件人和域名）、按规则预先放行（例如「发布到我自己的博客」）、批量确认。是否可行，需要用第 7 节的 S6 实测「每完成一个任务要确认几次」。

**另外两个缺口：**

- **代理混淆（confused deputy）。** 07 规划了 `agent.ask(task)`：应用把任务交给 Agent。如果 Agent 以 root 身份执行，一个只有 `notes: rw` 权限的应用就能借 Agent 读邮件。09 的公式「实际权限 = 调用方授权 ∩ 发起主体权限」是对的，但要明确写进 Run 模型：**应用发起的运行，权限上限是该应用的授权。**
- **持久化攻击面。** Agent 可以自己创建自动化（[02](../architecture/02-agent.md) 第 3.4 节），也可以安装应用；目前只会在活动流里通知。一个被注入的 Agent 可以创建一条「每收到邮件就转发给 X」的自动化，这是典型的持久化。**创建或修改包含对外出口的自动化、给应用授予权限，应当始终由用户确认，不受权限模式影响。**

### 3.3 effects 由宿主「判定」不可操作，应改为在出口把关 【高】

05 和 09 规定，工具的副作用等级（read / write / external / destructive）「由宿主在审核时判定」。可是生成工具的内部逻辑是任意 JS，宿主无从判定：一个叫 `notes.share` 的工具，内部可能调用 `agentos.net.fetch`。

AgentOS 有一个天然的优势：**应用没有网络，所有对外的副作用都必须经过宿主实现的系统服务**（`net.fetch`、`mail.send`、`publish`、授权文件夹之外的文件、EventKit 等）。所以：

- **工具的 effects 由能力推导，不必逐个判定。** 一个没有 `network`、`mail.send`、`publish` 授权的应用，它的所有工具最多是 `write`。
- **把关放在出口上。** 确认框在出口被调用时弹出，带上完整的调用链（哪个运行、由哪个事件触发、经过哪个应用的哪个工具）。这正好满足 [01](../architecture/01-shell.md) 第 3.3 节对确认框「展示来源链路」的要求。
- **effects 再细分一档。** 「能回滚就不用问」只覆盖 AgentOS 内部的状态。在 EventKit 里建日程、写进会同步到云端的文件夹，实际上已经出了 AgentOS，但事后还能删掉。建议区分 `external-reversible`（日程、草稿）和 `external-irreversible`（发信、发布、付款），活动流里每一条都标明能否撤销，而不是承诺「每条都能撤销」。

### 3.4 生成应用的「无界面执行」没有验证 【高】

整个协议和总线建立在一个前提上：应用没打开时，宿主可以用隐藏的 WebView 执行它的 `headless` 工具、处理它的持久订阅（05 第 4.1 节，03 第 5 节）。这个前提有三个问题：

1. **WebKit 会暂停不可见的页面。** P0 自己就遇到了「窗口被遮挡时 rAF 和渲染暂停」；`RuntimeManager` 给所有 WebView 设了 `inactiveSchedulingPolicy = .suspend` [代码]。不在窗口里的 WebView，定时器、Promise 和消息桥的行为都需要实测。
2. **生成的界面代码通常不能无界面运行。** 一启动就画 canvas、放音乐、绑键盘，和「被调用一个工具」毫无关系。
3. **热重载会打断订阅。** Builder 每改一次文件，页面就重载一次，订阅和进行中的工具调用怎么接续，没有定义。

**建议的应用模型（D2）：无界面核心 + 界面**，类似浏览器扩展的 background 加 popup，或 Android 的 Service 加 Activity：

```
apps/<id>/src/
├── core.js      # 工具、订阅、数据访问；不碰 DOM；在无界面宿主里运行
└── ui/          # 界面；通过 agentos.self.call(...) 调用自己的工具，或直接读写数据层
```

| 好处 | 说明 |
|---|---|
| 无界面执行可靠 | core 不碰 DOM，可以放进一个专用的隐藏 WebView（scheduling policy 设为 `.none`），空闲回收 |
| 接口和界面能力一致 | 界面也是自己接口的调用方，Agent 能做的和用户在界面上能做的天然一致 |
| 契约测试不依赖界面 | 测试只需要加载 core |
| 热重载更细 | 改界面不影响订阅；改 core 时宿主暂停投递、重载、再从游标补发 |

无界面宿主的选型对比见第 4.2 节。

### 3.5 「100% 接口覆盖」只保证有接口，不保证接口够用 【中】

「接口和应用一起诞生」能保证每个应用都**有**接口，但不能保证接口覆盖界面的能力：一个界面有 20 个功能的应用，可能只声明了 2 个工具。第 3.4 节的「界面调用自己的接口」是结构性的解法。评测指标也要相应改为「界面能完成的用户任务里，有多少能只通过接口完成」，而不只是「声明了的工具能否调用」（[11](../architecture/11-engineering.md) 第 4 节）。

### 3.6 协议层的几个歧义 【中】

| 歧义 | 现状 | 需要先定 |
|---|---|---|
| **工具和数据接口的分工** | 05 的示例里笔记应用提供 `notes.create`；08 又提供 `data.put('notes', …)`。新建一条笔记有两条路，Agent 走后一条就绕过了应用的逻辑 | 建议：增删改查一律走数据层；应用工具只做超出增删改查的行为（排版、导出、生成摘要）。或者规定集合有归属应用，写入必须经过它 |
| **命名空间归属** | 「数据长存，应用可抛」意味着同一个集合上可以有两个笔记应用；那么 `notes.*` 归谁？ | 工具按应用命名（`<应用短名>.<动作>`），领域名留给数据层 |
| **接口版本与兼容** | 应用 B 被重新生成后工具 schema 变了，调用它的应用 A 就坏了。这和「应用可抛」直接冲突 | 注册表根据 `calls` 声明知道谁依赖谁，安装时做 schema 差异检查，破坏性变更要么拦下，要么提升主版本；跨应用协作优先依赖共享数据 schema，而不是对方的工具 |
| **长任务、需要用户交互的工具、取消、并发** | 没有涉及 | 至少在 IDL 里预留 `long-running`、`interactive` 标记和取消语义 |

### 3.7 MCP 不宜作为内部真相源 【中】

方案已经提到「内部协议保持 MCP 形状，外面包一层适配器」，方向是对的，建议再进一步：

- 在宿主内部，「应用即 MCP Server」实际上是：JS 通过桥注册处理函数，宿主路由。真正需要说 MCP 的边界只有两个：面向 Agent（引擎把元工具注册成 SDK MCP 工具，再转给宿主，这和现在 `runtimeTools.ts` 的做法一样），以及面向原生、VM、远端应用的进程间传输。
- 所以应当**以 AgentOS 自己的接口定义（IDL）为真相源**：工具 schema、effects 上限、事件、订阅、依赖、版本。MCP、`aos` CLI、TypeScript 存根都是它的投影，和方案里 CLI 的定位一致。MCP 再有不兼容的大改，只需要改一个投影。
- 面向 Agent 时，P1 只用三个元工具（`apps.search`、`apps.describe`、`apps.call`），不在会话中途动态注入工具。这样实现最简单，提示缓存最稳定。SDK 虽然支持按需加载工具，但走 OpenRouter 时默认是关闭的（第 6 节）；用元工具，行为不随服务商变化。

### 3.8 P1 范围过大 【中】

P1 同时要交付：每个应用都是 MCP Server、事件总线、数据层 v1、`.agentpkg` 与回滚、能力授权与确认框、三档权限模式、effects、活动流、元工具、`aos` CLI、契约测试、共享 schema、多应用标签页、哈希链审计。这是 8 个模块的首个版本同时上线，任何一个设计返工都会拖住全部。拆分建议见第 5 节。

### 3.9 VM：最低系统版本和出站控制 【中】

- **系统版本冲突。** `project.yml` 的最低版本是 macOS 15，README 写的也是 15+；而 Containerization 和 vmnet 的新接口要求 macOS 26。建议直接把最低版本提到 macOS 26（2025 年 9 月发布），顺带可以用上 SwiftUI `WebView` 等新接口；否则 VM 相关的一切都要做成可选。
- **「NAT + 出站代理」自相矛盾。** [10](../architecture/10-workbench-vm.md) 写的是「每台 VM 用 vmnet 建立独立 NAT；所有出站流量都经过宿主代理」。VM 只要有一块能直通 NAT 的网卡，代理设置就只是建议，被注入的代码可以绕开。要真正强制，就不给 VM 直通的网卡，改用 vsock 加宿主侧的用户态网络栈（Lima 和 Podman 用的 gvisor-tap-vsock 一类），在宿主侧执行域名白名单。这个设计决定要在 P2 之前做。
- **P2 其实不需要 VM。** `web.fetch` 放进 VM 无头浏览器的理由是「避免在宿主进程里执行网页脚本」，但 WKWebView 本来就不在宿主进程里执行网页脚本：它跑在 Apple 沙箱化的 WebContent 进程里。用一个独立数据存储的隐藏 WKWebView 加 Readability 提取正文，就能满足研究助手。VM 真正不可替代的场景是工具链、应用后端和不可信代码，可以挪到 P3。这不改变「体验像 Parallels」的决定：那部分体验来自外壳，不来自 VM。

### 3.10 分发链路没有验证 【中】

11 第 7 节计划用 Developer ID 签名、公证，再用 Sparkle 更新；但现在 `ENABLE_HARDENED_RUNTIME: NO` [代码]。公证要求打开 hardened runtime，并且包里每个可执行文件都要用你的证书签名，包括 Bun 编译出的引擎和约 248 MB 的 claude 二进制。需要尽早确认三件事：Bun 编译的单文件能否正常签名和公证；重新签名 Anthropic 的 claude 二进制是否符合 SDK 条款；VM 需要的授权（`com.apple.security.virtualization`，以及网络相关的授权是否属于受限授权）能否用于 Developer ID 分发。任何一项不通过，都会影响引擎和 VM 的架构。

### 3.11 引擎扩展到 Operator 后的进程与成本模型 【中】

Agent SDK 每个会话拉起一个 claude 子进程（[architecture-research.md](architecture-research.md) 第 4.2 节）。Builder 一次一个，没有问题；但 Operator 加上事件触发的自动化，会出现多个会话并发，常驻内存和费用都会放大。建议引擎内部分两种执行方式：

| 执行方式 | 用于 | 实现 |
|---|---|---|
| 完整 Agent | Builder、交互式 Operator、复杂自动化 | Agent SDK `query()` |
| 单次模型调用 | 隔离模型解析不可信内容、路由、起名、自动化里的简单步骤 | 直接调用 Messages API，用结构化输出，不带工具 |

隔离模型本来就不该有工具，用完整的 Agent SDK 反而多了风险面。

费用上限也要由宿主执行：SDK 的 `maxBudgetUsd` 是客户端估算，可能超支（第 6 节）。自动化的每日次数和费用上限，应当由宿主按 Run 记账并强制执行。

### 3.12 其他

- **模型侧的数据流出。** Agent 能读全部数据，读到的内容都会发给模型服务商。经 OpenRouter 时，实际承接请求的服务商和数据保留政策各不相同。建议让 `sensitivity` 标签也约束「哪些数据可以发给哪类模型」，例如实验性模型不能读 `private` 数据。
- **本机签名对 A 类应用意义不大。** 签名者和校验者是同一台机器、同一个宿主；能改数据目录的攻击者已经控制了用户账户。签名和构建证明对 C 类和导入导出才有价值，P1 可以只用内容摘要加 git。
- **文档不一致：**
  - Containerization 的版本：[system-architecture.md](system-architecture.md) 的表格写「1.5.0」，[10](../architecture/10-workbench-vm.md) 第 8 节写「才 1.0 不久（2026 年 6 月）」。核实结果：1.5.0 是 `container` 命令行工具的版本，被嵌入的 `containerization` 包是 0.51.0，仍未到 1.0（第 6 节）。
  - 06 号分册说总线「形状对齐 MCP 事件草案」，但草案的方法名和语义已经不同（第 6 节）。
  - 愿景第 2 节原则 5 写「应用和 Agent 都只拿到声明并获得授权的能力」「发邮件、删除、发布、付款由宿主弹出确认」，和后来的「Agent ≈ root、自动模式不确认」冲突。愿景已标注部分内容被取代，但这一条没有标注。
  - 最低系统版本：工程是 macOS 15，VM 需要 26。

## 4. 关键选型的横向对比

### 4.1 应用协议的真相源

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| MCP 原样作为内部协议 | 标准、Agent 原生理解 | 版本变动大（2026-07-28 就是一次不兼容的大改）；没有 effects、依赖、版本兼容这些 AgentOS 需要的概念 | 不建议作为真相源 |
| **自有 IDL + 多种投影（MCP、CLI、TS 存根）** | 能表达 effects 上限、依赖和兼容规则；MCP 变动只影响一个投影 | 要自己维护一份 schema 规范 | **推荐** |
| App Intents 风格的带类型实体 | 实体和共享 schema 的建模很成熟 | 绑定 Swift，生成的 JS 应用用不上 | 借鉴它的「共享领域 schema」，不照搬 |
| 纯 postMessage RPC | 最简单 | 没有发现、没有 schema，Agent 无法使用 | 不采用 |

### 4.2 应用核心的无界面执行宿主

| 方案 | 隔离 | 开销 | 和现有安全模型的复用 | 风险 |
|---|---|---|---|---|
| **专用隐藏 WKWebView（每个活跃应用一个）** | WebContent 进程级 | 每个实例一个 WebContent 进程，几十 MB 起 | **完全复用**（CSP、规则列表、origin 校验） | 不在窗口里的行为要实测（S1） |
| 界面 WebView 里的 Web Worker | 同界面 | 低 | 复用 | 界面关闭，Worker 就没了，不满足无界面执行 |
| JavaScriptCore 上下文，放在一个沙箱化的 XPC 辅助进程里 | 进程级（多个应用共进程时只有语言级隔离） | 每个上下文几 MB | 需要重做桥接和授权 | 工作量中等；多个应用共用一个进程时隔离较弱 |
| WASM 组件（Wasmtime 或 WasmKit） | 能力级，最强 | 低 | 需要重做 | 模型写 JS 最熟练，写 WASM 组件可靠度低 |

**结论：** P1 用专用隐藏 WKWebView，加上空闲回收和并发上限；规模上来之后，再评估 XPC 加 JSC。

### 4.3 事件总线

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **自建：CloudEvents + SQLite 追加日志（方案现状）** | 和数据层同一套存储；可以审计、可以回放；没有外部依赖 | 要自己实现游标、背压、补发 | **保留**，但 P1 收窄范围 |
| 内嵌 NATS JetStream | 持久消费者、通配授权都是现成的 | 多一个 Go 进程；授权模型和 AgentOS 的能力授权要做两遍 | 不采用（借鉴它的授权和背压设计） |
| 只用数据变更事件（数据库触发器） | 最简单；「数据长存」原则下大部分协作本来就是围绕数据 | 表达不了「播放开始」这类和数据无关的事件 | **作为 P1 的第一步** |
| MCP 通知或事件草案 | 标准 | `subscriptions/listen` 只能通知「资源变了」；事件草案没有被接纳，语义还在变（推送用 `events/stream`，`events/subscribe` 只用于 webhook，游标由客户端保管） | 只在对外适配时考虑 |

**P1 收窄：** 先只做 `data.<集合>.changed` 加系统事件，以及应用和 Agent 的持久订阅；应用自定义事件放到 P1b。笔记加待办的演示用数据订阅就能完成：待办应用订阅 `data.notes.changed`，读取正文，抽出 TODO。

### 4.4 Agent 引擎

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Claude Agent SDK sidecar（现状）** | Agent 循环、hooks、会话、MCP、子 Agent 都现成；P0 已验证 | 248 MB 二进制；每个会话一个进程；内置行为偏向编程场景 | **保留**，用于完整 Agent |
| Swift 原生循环 + Messages API | 体积小、进程内、完全可控 | 要自己写会话、压缩、重试、工具循环 | **作为补充**，用于单次模型调用（第 3.11 节） |
| 经 ACP 接入多引擎 | 引擎可替换 | 宿主需要的是运行时工具和权限集成，不只是对话协议 | 低优先级；保持协议形状即可，不必实现 |
| 多厂商循环（Vercel AI SDK、pi） | 换模型方便 | 失去 Claude Code 现成的工具和 hooks | 只有当非 Claude 模型成为主线时才考虑 |

### 4.5 权限框架

| 范式 | 代表 | 适合 AgentOS 的部分 |
|---|---|---|
| 清单式权限（安装时一次性授予） | Android 早期 | 应用申请的基线 |
| **能力（capability）** | Fuchsia、Plan 9 | 订阅、调用、数据集合的授权：可限定范围、可撤销、可过期（方案现状） |
| **信息流标签** | FIDES、CaMeL | 污点和机密性标签，作用在运行、应用实例、记录三个层级（第 3.2 节） |
| 策略引擎 | Cedar、OPA | 用户的例外规则（「发给公司域名时放行」）。规则少，不必引入引擎，手写一个小的求值器即可 |

**推荐组合：** 能力授权决定「能不能做」，信息流标签决定「要不要确认」，两者都在出口上的单一检查点执行。

### 4.6 数据层

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **SQLite + JSON 文档 + JSON Schema 校验 + FTS5（方案现状）** | 适合生成应用多变的结构；查询、事务、历史都好做 | 跨集合的关系查询要自己约定 | **推荐** |
| 每个集合一张强类型表 | 查询性能好 | schema 变更要做迁移，不适合生成应用 | 不采用 |
| CRDT（Automerge 等） | 将来多设备同步方便 | 多设备同步不在路线图上；复杂度高 | 不采用 |
| 文件优先（类似 Obsidian） | 用户看得见、带得走 | 查询和订阅弱；外部修改需要监听和对账 | 只用于文档正文，P2 再做 |

见第 6 节末尾的表格。

## 5. 先行设计详解与修订后的路线图

### 5.1 D1 内核对象模型与单一检查点

**为什么最先做：** 授权、审计、活动流、撤销、预算、污点，全都要挂在同一组对象上。现在这些概念散落在 06、08、09 里，各自引用 `traceparent`，但没有一个统一的定义。

| 对象 | 内容 |
|---|---|
| 主体（Principal） | `user`、`agent-run:<id>`、`app:<id>`（细分到实例）、`service:<name>`、`automation:<id>`、`cli:<token>` |
| 能力（Grant） | 持有者、能力类型、范围、来源（谁授予）、过期、撤销 |
| 运行（Run） | 一次自主工作：发起主体、委托链、触发原因、预算、污点标签、trace id |
| 效果日志（Effect） | 每一次写入或出口调用：属于哪个 Run、能否撤销、怎样撤销 |

**检查点的入口清单：** 工具调用、数据读写、事件发送与订阅、出口服务、scheme handler、导航、消息桥、CLI socket。

**要回答的问题：** 委托链怎样求交集；Run 和会话的关系；实例级标签什么时候清除；效果日志怎样支撑活动流的撤销。

### 5.2 D2 应用模型与接口 IDL

- 无界面核心加界面（第 3.4 节）。
- IDL 字段：工具（输入输出 schema、`long-running`、`interactive`）、事件、订阅、依赖（`calls`）、数据集合、版本和兼容规则；effects 由能力推导，不由应用声明。
- 投影：Agent 元工具（`apps.describe` 返回的内容）、MCP（给原生和 VM 应用）、`aos` CLI、TS 存根（代码模式）。
- Builder 的生成顺序：数据模型 → core 的工具 → 契约测试 → 界面。

**验证：** S1、S4。

### 5.3 D3 数据层 v1

P1 只做集合（`notes`、`tasks`、`documents`），不做文件索引。先定三件事：集合的归属和写入路径（第 3.6 节）、`ext.<appId>.*` 扩展字段的规则、历史表的保留策略。

### 5.4 D4 权限策略与出口把关

- 出口清单和每个出口的 effects 等级。
- 三档模式在「运行级污点」定义下的精确行为。
- 始终需要用户确认的操作：给应用授权、创建或修改包含出口的自动化、关闭沙箱回归用例里的任何一项防护。
- 确认框的信息设计：参数、来源链路、能否撤销、「以后同类直接放行」。

**验证：** S6。

### 5.5 D5 Agent 引擎架构

- 会话模型：全局对话由 Operator 承接；Builder 作为子 Agent，还是单独的会话？每个应用的 Builder 会话要不要保留？
- 工具暴露：P1 只用三个元工具；运行时工具、包管理工具常驻。
- Run 集成：每次 `query()` 对应一个 Run，预算和污点挂在 Run 上。
- 两种执行方式（第 3.11 节）。
- 评测集：10 个游戏加协议演示，持续跟踪一次通过率、成本、修复轮数和接口覆盖率。

### 5.6 修订后的路线图建议

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1a 内核与单应用协议** | 修复越界读取并补沙箱回归用例；D1 内核对象模型；D2 应用模型（core 加界面）和 IDL；JS SDK（`tools.register`、`data`、`self.call`）；数据层 v1；Agent 元工具；git 版本和回滚；只读的活动流 v0；评测集；最低系统版本提到 macOS 26 | Builder 生成一个带接口的笔记应用；Agent 通过 `apps.call` 操作它；Agent 的一次写入能从活动流撤销；沙箱回归用例全部通过 |
| **P1b 应用互联与订阅** | 总线 v1（数据变更、系统事件、持久订阅）；能力授权界面和跨应用调用；自动化（定时和事件触发，工具白名单固定）；`aos` CLI；接口兼容检查 | 笔记加待办演示；重新生成笔记应用后，待办应用不受影响 |
| **P2 第一条纵向链路** | Operator；`web.search`、`web.fetch`（隐藏 WKWebView 加正文提取）、浏览器视图；`publish`；**运行级污点和出口把关（发布门槛）**；文件服务 | 「研究 X 并写成博客草稿」一句话完成；在页面里放一段注入文本，不会造成未经确认的发布 |
| **P3 工作间与通信** | Workbench VM（不给直通网卡）；邮件服务；隔离模型解析和先计划后执行；媒体 | 邮件触发的自动化可控、可审计 |
| **P4 原生与演化** | B 类本地编译；可生成外壳和恢复模式；WASM；C 类云构建按需 | 同原方案 |

## 6. 外部前提核实

截至 2026-10-15，按官方文档、规范仓库和源码核实：

| 前提 | 文档中的说法 | 核实结果 | 对方案的影响 |
|---|---|---|---|
| MCP 2026-07-28 | 无状态，去掉 `initialize` 和会话；`server/discover`；`subscriptions/listen` 只通知变化；Tasks 改为扩展 | **属实**，且是当前版本。另有两点文档没提：服务端到客户端的请求改成了多轮往返模式；列表结果必须带 `ttlMs` 和 `cacheScope`。MCP Apps 早在 2026-01-26 就成了官方扩展，不是 2026-07-28 才成为 | 印证「MCP 变动大」，支持第 3.7 节「IDL 为真相源」 |
| MCP 事件草案 | 总线「形状对齐草案」：`events/list`、`events/subscribe`、通知、游标、`events/ack` | **部分不符。** 草案（2026-09-08 合入的设计草图，没有被接纳为 SEP）的投递方式是 `events/poll`、`events/stream`（推送），`events/subscribe` **只用于 webhook**；游标由客户端保管，没有 `ack`；事件是带参数的「事件源」，不是「类型加过滤条件」。工作组章程确实排除了通用发布订阅 | 总线是内部的，不受影响；但「将来可以和标准合流」要么把方法名对齐草案，要么删掉这条承诺 |
| ACP | 引擎协议按 ACP 的形状设计，将来可替换 | 属实。ACP 很活跃（schema v1.25.0），Codex、Gemini CLI、OpenCode 等都已接入。Claude 的适配器 `claude-agent-acp` 由 ACP/Zed 维护，基于 Agent SDK，**不是 Anthropic 官方的** | 可替换性成立，维持低优先级 |
| Apple Containerization | 「1.5.0」（调研表格）；「才 1.0 不久」（10 号分册） | **两处都不准确。** 1.5.0 是 `container` 命令行工具的版本（2026-09-29）；被嵌入的 `containerization` Swift 包是 **0.51.0，仍未到 1.0**。要求 Apple 芯片和 macOS 26。还需要随应用分发 Linux 内核和 `vminitd` | API 不稳定的风险比文档写的更大；最低系统版本必须提到 26 |
| VM 网络授权 | 用 vmnet 建立独立 NAT | 默认的 NAT 网卡只需要 `com.apple.security.virtualization`（不受限，Developer ID 可用）。macOS 26 新的 vmnet 网络：Apple 自己的 `container` 只用了这一项授权，但 vmnet 的官方文档仍写着沙箱进程需要受限的 `com.apple.vm.networking`。**不给网卡、只走 vsock 是可行的**：Containerization 默认不配网卡，可以接入自定义的网络附件（vfkit 加 gvproxy 的做法） | 印证第 3.9 节：用 vsock 加用户态网络栈强制出站白名单；vmnet 方案要在 Developer ID 签名下实测（S5、S7） |
| WebRTC | 文档没有涉及 | WKWebView **没有公开 API 关掉 WebRTC**，只有私有的 `_peerConnectionEnabled`。WebKit 的 `connect-src` 不管 WebRTC 和 ICE。CSP 的 `webrtc` 指令没有任何浏览器实现 | 印证第 2.3 节。AgentOS 不上 App Store，可以评估使用私有开关；注入脚本删除构造函数只能作为补充 |
| Claude Agent SDK | 进程内 MCP、hooks、`dontAsk`、会话恢复、预算、按需加载工具 | 全部属实。两点要注意：① 工具搜索默认开启，也作用于 SDK MCP 工具，但当 `ANTHROPIC_BASE_URL` 指向非官方地址时（**也就是走 OpenRouter 时**）默认关闭，要设 `ENABLE_TOOL_SEARCH=true`；② `maxBudgetUsd` 是客户端估算，可能超支。另外确认必须随应用分发 claude 原生二进制 | ① 支持第 3.7 节「P1 只用元工具」，行为不随服务商变化；② 自动化的每日费用上限要由宿主记账执行，不能只依赖 SDK |
| GitHub Actions 计费 | `macos-26` 约 $0.062/分钟 | 属实（标准 macOS runner，2026-02-26 起提供 `macos-26`）；公开仓库免费 | 无 |

**同类产品（截至 2026-10）：** 没有找到哪家大厂在做「本地桌面上、由模型生成可长期使用的应用」的系统。最接近的几类：

| 产品 | 做什么 | 和 AgentOS 的区别 |
|---|---|---|
| Imagine with Claude | 2025-09 的 5 天研究预览，在云端沙箱里即时生成软件 | 用完即弃；没有应用接口和总线 |
| Claude Artifacts | 生成的应用托管在 claude.ai，可以用 MCP 连接器，有持久存储 | 应用是 MCP 的消费者，不是 MCP Server；没有应用之间的总线 |
| Gemini Dynamic View | 针对每个提问生成一次性的 HTML/JS 界面 | 一次性的回答，没有持久化和互通 |
| Google Opal | 用自然语言搭 AI 小应用工作流，存在 Drive 里 | 云端的工作流链，不涉及系统集成 |
| OpenAI Apps SDK | 开发者手写的 MCP Server 加界面，在 ChatGPT 里运行 | 应用是人写的，不是生成的；宿主是 ChatGPT |
| MCP Apps 扩展 | `ui://` 资源放在沙箱 iframe 里渲染；Claude、ChatGPT、VS Code、Goose 都支持 | 最接近「应用 = MCP Server + 界面」的标准，AgentOS 的界面层应向它对齐 |
| Windows 的 MCP 注册表 | 系统级代理，为 MCP 连接器统一处理身份、授权和审计（预览中） | 架构上最接近「宿主是唯一的 MCP 客户端」；但连接器是安装的，不是生成的，也没有事件总线 |
| Websim | 用自然语言生成可分享的网页和应用 | 网页托管；没有 MCP、本地宿主和总线 |

**结论：** 「生成的应用必须同时交付接口，并通过系统级总线互通」这个组合目前没有人在做，差异化成立。但单项能力（生成界面、MCP 应用、系统级 MCP 代理）大厂都在推进，**护城河在于把它们整合成一个可信的本地系统**，也就是第 3 节那些问题能不能做对。

## 7. 建议的技术验证（Spike）

| # | 问题 | 方法 | 通过标准 |
|---|---|---|---|
| S1 | 不在窗口里的 WKWebView 能否可靠地执行 JS | scheduling policy 设为 `.none`，测定时器、Promise、消息桥、`callAsyncJavaScript` 在不同可见性下的行为，以及每个实例的内存 | 工具调用 p95 延迟小于 200 ms；连续 1 小时不被挂起；每个实例的内存有明确数字 |
| S2 | 运行时隔离加固 | 修复越界读取；宿主钩子放进独立 content world；关闭 WebRTC（公开 API 不够时评估私有开关或注入所有 frame）；把探针加入回归 | 三个探针加原有的 `sandbox-escape` 全部被拦截 |
| S3 | Agent 面对大量工具的准确率 | 合成 50、100、200 个应用工具，对比「三个元工具」和「延迟加载」两种方式 | 选出准确率和成本更好的一种，作为 D5 的依据 |
| S4 | Builder 能否稳定地交付接口 | 让 Builder 按 core 加界面的结构生成笔记、待办、书签各 10 次 | 契约测试一次通过率；界面任务中只靠接口能完成的比例 |
| S5 | 分发链路 | 打开 hardened runtime，对引擎和 claude 二进制签名并公证；接入 Sparkle | 公证通过，在一台干净的 Mac 上能启动并调用模型 |
| S6 | 确认框频率 | 在运行级污点定义下，跑 20 个研究和整理类任务 | 每个任务平均确认次数小于 1 |
| S7 | VM 出站控制（P3 之前） | 不给 VM 直通网卡，用 vsock 加用户态网络栈，在宿主侧执行白名单 | VM 里的进程无法绕过白名单访问外网 |
