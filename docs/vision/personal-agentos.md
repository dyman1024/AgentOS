## 1. 愿景

AgentOS 是一台**生成式的个人电脑**：电脑在应用层能做的事情，它都能做，比如开发和玩游戏、上网查资料、收发邮件、看电影、写文档和博客。不同之处在于，这些应用不是预装的，而是用户和 Agent 在使用过程中不断生成、修改、组合出来的。每个人的 AgentOS 最终都长成自己的样子。

这和 P0 原型的定位不同：

| | P0（应用生成器） | Personal AgentOS |
|---|---|---|
| 应用 | 互相隔离的单文件小程序，不能联网、看不到用户数据 | 能联网、能读写个人数据、能互相协作的应用 |
| Agent | 只负责「造应用」 | 既造应用，也直接替用户办事，还能驱动应用 |
| 数据 | 每个应用自己的 localStorage | 系统级个人数据，应用只是数据之上的视图 |
| 系统本身 | 固定的 Swift 外壳 | 外壳之上的一切都可以生成，只有一个最小的可信内核不可生成 |

## 2. 设计原则

1. **数据长存，应用可抛。** 个人数据（文档、邮件、书签、媒体库、笔记）存在系统级数据层，应用只是这些数据上的视图和工作流。应用可以随时重写、替换、分叉，数据都不会丢。
2. **能用确定性服务的，就不要生成。** 网络协议、邮件收发、视频解码、密钥管理、文件访问都由可信的系统服务实现，测试充分且稳定。生成的部分集中在界面、工作流和个性化上。不能让模型每次都用 JS 重写一个 IMAP 客户端。
3. **对话是主入口，应用是「固化的工作流」。** 用户先在对话里让 Agent 直接办事；某件事反复做，Agent 就提议把它固化成应用；应用反过来也可以调用 Agent。
4. **最小可信内核，其余皆可生成。** 权限、密钥、版本回滚、恢复模式、Agent 运行时属于内核，不可生成。启动台、Dock、小组件这类外壳，以及所有应用，都可以生成，坏了能一键回滚。
5. **最小权限，敏感操作由人确认。** 应用和 Agent 都只拿到声明并获得授权的能力。发邮件、删除、发布、付款这类操作，由宿主弹出确认，不能由应用界面自己确认，因为应用界面可以伪造。来自网页和邮件的内容一律当作不可信数据。
6. **对齐开放标准。** 应用与宿主之间的协议对齐 MCP Apps，外部集成用 MCP Server 当「驱动」。

## 3. 分层架构

```
┌──────────────────── 生成层：可生成、可迭代、可回滚 ────────────────────┐
│ 应用：游戏 · 研究助手 · 邮件 · 媒体库 · 文档/博客 · …                     │
│ 系统外壳：启动台 · Dock · 小组件 · 主题                                   │
├──────────────────── 应用运行时 + UI Kit ──────────────────────────────┤
│ 每个应用一个沙箱 WebView（P0 已有）· agentos.* SDK（JSON-RPC，对齐 MCP Apps） │
│ 系统组件：富文本编辑器 · 代码编辑器 · 视频播放器 · 浏览器视图 · 图表 · Markdown │
├──────────────────── 系统服务：可信，Swift 实现，按权限开放 ─────────────┤
│ 数据：个人数据库（集合 + 全文/语义检索）· 文件（用户授权的文件夹）          │
│ 网络：按应用白名单的 fetch · 搜索 · 网页抓取 · 浏览器                       │
│ 通信：邮件（IMAP/SMTP）· 通知 · 后台任务与同步                              │
│ 媒体：本地媒体库 · 播放（WebKit 解码，必要时原生播放器）                     │
│ 智能：agentos.ai · 调用 Agent · 记忆与个性化                                │
│ 集成：MCP 驱动（日历、GitHub、Notion…）· 应用间 Intent（「用…打开」「分享到…」）│
├──────────────────── Agent 层 ─────────────────────────────────────────┤
│ Builder：造应用、改应用 · Operator：直接办事、驱动应用 · 记忆                 │
├──────────────────── 可信内核（不可生成）────────────────────────────────┤
│ 权限与审计 · 密钥保管 · 版本、回滚与恢复模式 · 进程与窗口管理 · 模型服务商       │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.1 应用清单与权限

每个应用都有一份清单，声明它需要的能力。用户首次使用时授权，之后可以在设置里随时撤销：

```jsonc
{
  "id": "…", "title": "研究助手", "icon": "🔎",
  "permissions": {
    "network": ["api.github.com"],                       // 只放行这些域名
    "data": { "notes": "rw", "bookmarks": "rw", "emails": "r" },
    "services": ["web.search", "web.fetch", "ai.complete", "mail.send:confirm"],
    "files": ["~/Documents/Blog"]                        // 用户授权过的文件夹
  }
}
```

### 3.2 agentos.* SDK（应用侧）

```ts
agentos.data.collection('notes').query({ text: '强化学习' })   // 个人数据，按集合授权
agentos.web.search('…') / agentos.web.fetch(url)              // 由宿主执行，受白名单约束
agentos.browser.open(url)                                       // 打开一个真正的浏览器视图（不受沙箱限制）
agentos.mail.list({ folder: 'INBOX' }) / agentos.mail.send(draft) // 发送前由宿主确认
agentos.media.library() / agentos.media.play(id)
agentos.files.pick() / agentos.files.read(path)                 // 只能访问授权的文件夹
agentos.ai.complete(prompt) / agentos.agent.ask(task)           // 应用调用 AI 或 Agent
agentos.intent.open('document', ref) / agentos.notify(…)
agentos.tools.call('mcp_server.tool', args)                     // MCP 驱动，对齐 MCP Apps
```

### 3.3 两种 Agent

- **Builder**：P0 已有。负责造应用、改应用、测试、修复。
- **Operator**：新增。直接替用户办事，用到的工具包括网页搜索和抓取、读写个人数据、调用系统服务、驱动已有应用。
  - 处理网页、邮件这类不可信内容时，自动收紧权限，比如不允许直接发信。
  - 某件事反复出现时，提议「固化成应用」，交给 Builder。

## 4. 用户提到的场景如何落地

| 场景 | 生成的部分 | 系统服务和组件 | 难点 |
|---|---|---|---|
| **开发和玩游戏** | 游戏本身 | 运行时（已有）；以后加原生模式处理 Metal 或 120Hz | 复杂游戏的质量，靠 Skill 模板和评测集提升 |
| **上网搜资料** | 研究助手：搜索、摘录、整理、引用管理 | `web.search`、`web.fetch`、浏览器视图、数据层（书签和笔记） | 网页内容可能带提示注入；网站禁止被 iframe 嵌入，所以必须用浏览器组件；经 OpenRouter 时 WebSearch 是否可用待验证 |
| **邮件** | 邮件客户端界面、分类规则、AI 摘要和回复草稿 | `mail` 服务（IMAP/SMTP，凭据只在宿主侧）、后台同步、通知 | Gmail 的 OAuth 受限权限需要 Google 审核，先支持 IMAP 应用专用密码（QQ、163、Gmail 都可以）；邮件里的提示注入；发信必须确认 |
| **看电影** | 片库、海报墙、观看记录、推荐 | `media` 服务：扫描授权的文件夹，自定义 scheme 支持 Range 请求以便拖动进度条 | WebKit 不支持 MKV 等容器格式，需要原生播放器组件（例如 libmpv）；在线流媒体有 DRM，只能交给浏览器组件 |
| **写文档和博客** | 写作应用、博客后台、排版主题 | 文件服务（Markdown 存在用户文件夹里，方便和其他工具互通）、编辑器组件、`ai` 写作辅助、发布服务（GitHub Pages、Ghost、WordPress 等，发布前确认） | 编辑器质量必须靠内置组件，不能临场生成 |

能力边界，即短期内不追求的：

- 专业级重型应用：视频剪辑、音频工作站、大型 IDE、3A 游戏。可以通过 AppleScript、快捷指令或辅助功能接口驱动已有的 Mac 应用来补位。
- 需要内核扩展的能力，以及 DRM 流媒体的内嵌播放。

## 5. 风险

1. **提示注入是头号风险。** 一旦接入邮件和网页，就会有恶意内容试图指挥 Agent。对策有四条：不可信内容只当数据处理、按场景收紧工具权限、敏感操作由宿主确认、留审计日志。
2. **应用长期迭代后变质。** 每个应用维护一份由 Agent 更新的「规格说明」，再保存一组冒烟测试，保证意图和质量能跨会话延续。
3. **成本。** 一个个人 OS 意味着大量应用和持续迭代。要靠组件复用、模板、提示词缓存降低成本，按任务选择模型（必要时用本地模型）。
4. **后台运行。** 邮件同步等任务需要在主窗口关闭后继续跑，需要登录项或常驻辅助进程。
5. **范围失控。** 「电脑能做的都能做」没有边界，必须用具体场景驱动平台建设，一次只打通一条纵向链路。

## 6. 路线图（修订）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0**（已完成） | 运行时、Builder Agent、自测闭环、OpenRouter | 一句话生成可玩的游戏 |
| **P1 平台底座** | 多应用并行与多窗口；`agentos.*` SDK v1（数据层、文件、通知、`ai`）；权限清单与授权界面；UI Kit 与内置组件；每个应用一个 git 仓库，支持版本和回滚；评测集 | 生成的应用能读写个人数据，并能互相打开对方的内容 |
| **P2 联网与内容**（第一条纵向链路） | 网络服务和浏览器组件；Operator Agent；记忆；**研究助手 → 文档/博客**整条链路 | 一句话「研究 X 并写成博客草稿」：搜索、整理、成文、存进文档库，全程可追溯 |
| **P3 通信与媒体** | 邮件服务和后台同步；媒体库和播放器；应用间 Intent；MCP 驱动；发布服务 | 用 AgentOS 收发日常邮件、管理并播放本地影片 |
| **P4 自我演化** | 可生成的系统外壳和恢复模式；应用分享和导出；原生模式；本地模型 | 用户能重新设计自己的桌面，坏了一键恢复 |
